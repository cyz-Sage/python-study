# AI 知识助手（命令行版）

一个基于大模型 API 的本地知识库问答助手。它在命令行中接收提问，**强制模型只依据本地知识库文件回答**，并把每一轮对话持久化到 SQLite 数据库中。

> 当前版本：v1.0 ｜ 技术定位：RAG（检索增强生成）的雏形

## 这个项目解决什么问题

直接问大模型，它会用网上的一般性知识回答，涉及你的私有资料时就开始编造（幻觉）。

本项目的做法是：启动时读取本地知识库文件，把内容注入到系统提示词中，并加上「请严格根据以下背景信息回答问题」的约束。这样当资料里没有答案时，模型会回答「根据我掌握的信息无法回答」，而不是瞎猜。

## 功能特性

- **本地知识库问答**：读取 `notes.txt` 作为背景知识，回答严格受限于资料内容
- **多轮对话记忆**：维护 `messages` 列表累积上下文，模型能记住前面聊过什么
- **上下文窗口截断**：只保留最近 20 条历史发给模型，避免越聊越贵、最终超出模型长度上限
- **对话持久化**：每轮问答（时间 / 问题 / 回答）写入 SQLite，可用 Navicat 等工具直接查看
- **密钥与代码分离**：API Key 存放在 `.env` 文件中，通过 `os.getenv()` 读取，不进入代码仓库
- **路径锚定**：所有文件路径以脚本自身位置为基准，在任何目录下运行结果一致
- **健壮性处理**：30 秒请求超时 + HTTP 状态码校验 + 超时/连接失败/未知异常分类捕获
- **知识库缺失告警**：找不到知识库文件时明确警告「AI 可能会编造内容」，而非静默降级

## 快速开始

### 1. 环境要求

- Python 3.10 或以上
- 一个 DeepSeek API Key（在 [platform.deepseek.com](https://platform.deepseek.com) 申请）

### 2. 安装依赖

```bash
pip install requests python-dotenv
```

如果使用 `uv` 管理环境，虚拟环境默认不带 pip，请改用：

```bash
uv pip install requests python-dotenv
```

### 3. 配置 API Key

在仓库根目录创建 `.env` 文件：

```
DEEPSEEK_API_KEY=你的key
```

**注意：不要把 Key 写进源码，也不要提交 `.env`。** 仓库已用 `.gitignore` 排除 `.env`、`.venv/`、`__pycache__/`、`chat_history.db`。

### 4. 运行

```bash
python ai-helper/main.py
```

启动后会看到：

```
[信息] 已加载知识库：...\ai-helper\notes.txt（57 个字）
开始聊天吧！（输入'退出'结束程序）

你：
```

### 5. 使用示例

假设 `notes.txt` 内容为：

```
我的宠物叫旺财，是一只3岁的柯基犬。
旺财对花生过敏，绝对不能吃任何含花生的食物。
旺财每天需要出门散步两次，每次半小时。
```

| 你输入 | AI 回答 |
| --- | --- |
| `旺财能吃花生吗？` | 不能，旺财对花生过敏，绝对不能吃任何含花生的食物。 |
| `旺财是什么性别？` | 根据我掌握的信息，没有提到旺财的性别，所以我无法回答这个问题。 |

第二个问题资料里确实没有答案，模型如实回答「无法回答」而不是编造——**这正是本项目要验证的核心效果**。

## 设计要点与踩过的坑

这一节是项目里最有价值的部分，记录了开发过程中真实遇到的问题。

**1. 相对路径依赖「终端当前目录」，而不是脚本所在目录**

最初写的是 `sqlite3.connect("chat_history.db")` 和 `open("ai-helper/notes.txt")`。在项目根目录运行时碰巧正确，但一旦 `cd ai-helper` 再运行，就会因为找不到 `notes.txt` 而让模型开始编造，同时新建一个空的数据库文件，看起来像「历史记录丢了」。

修复方式是用 `__file__` 锚定脚本自身位置：

```python
BASE_DIR = Path(__file__).parent      # 脚本所在文件夹
ROOT_DIR = BASE_DIR.parent            # 仓库根目录，用于找 .env
NOTES_PATH = BASE_DIR / "notes.txt"
DB_PATH = BASE_DIR / "chat_history.db"
```

修复后，脚本在任何目录下运行、拷到任何电脑上，结果都一致。

**2. 对话历史无限增长**

每一轮都往 `messages` 追加两条消息，并每次都发送完整历史。聊 50 轮就是带着 100 条历史去请求，费用成倍上升，最终还会因为超出模型上下文上限而失败。

修复方式是在构造本次请求时做滑动窗口截断：

```python
MAX_HISTORY = 20
recent_history = messages[1:][-MAX_HISTORY:]
```

**3. 找不到知识库时静默降级，是最危险的失败方式**

最初的写法是捕获 `FileNotFoundError` 后把 `knowledge` 设成一句提示，程序若无其事地继续跑。结果是 AI 开始编造宠物信息，而使用者以为它读了笔记——「看起来正常，其实全错」比直接崩溃危险得多。

修复方式是启动时只读一次，文件不存在就大声警告：

```
[警告] 没找到知识库文件：...\ai-helper\notes.txt
        本次回答没有背景知识，AI 可能会编造内容！
```

**4. 密钥硬编码**

早期版本把 API Key 直接写在源码里。GitHub 上存在专门扫描 `sk-` 开头字符串的爬虫，密钥泄露后会被他人消耗额度。现已改为 `.env` + `os.getenv()`，并用 `.gitignore` 排除。

## 验证「幻觉」的对比实验

把 `notes.txt` 临时改名为 `notes_bak.txt`，再问同一个问题：

- **正常情况**：`旺财能吃花生吗？` → 模型依据资料回答「不能，它对花生过敏」
- **知识库缺失**：同一个问题 → 模型一本正经地编造「柯基犬是可以吃花生的」

这个对比就是「幻觉」（Hallucination）现象，也是本项目采用知识库注入的原因。

## 已知局限

- **知识库整体注入提示词**：当前把整篇资料塞进 system 提示词。资料只有几行时可行，当资料有数万字时既塞不进去、也会带来明显的费用和延迟开销
- **无检索环节**：没有文档切分、向量化和相似度检索，全部内容无差别地送入模型
- **仅支持单文件、纯文本**：不支持多文档、PDF、Word 等格式
- **仅命令行交互**：没有图形界面，无法演示给非技术人员
- **无并发与用户隔离**：单用户、单会话，历史记录不区分会话
